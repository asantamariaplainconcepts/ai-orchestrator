# Design — azure-dev-infrastructure

## D1 — One root module per environment, no premature module library

`infra/dev/` is a flat root module. A `modules/` library with one consumer is the infrastructure
version of the speculative seam RULE-007 rejects; the second environment (prod) is the moment
extraction earns its keep, with a real second consumer to shape it.

## D2 — State backend precedes Terraform, by script, not by hand-waving

Remote state needs a storage account that Terraform itself cannot create (chicken-and-egg). A
small idempotent script (`infra/bootstrap.sh`, az CLI) creates `rg-aio-tfstate`, a storage
account, and a `tfstate` container, then prints the backend config. Running it twice is safe;
its output is the input to `terraform init`. Local state was rejected (no locking, easy to
lose); Terraform Cloud was rejected (a second external service for a solo project).

## D3 — The subscription id is configuration, never code

The repo is public. `subscription_id` arrives via gitignored `terraform.tfvars` or
`ARM_SUBSCRIPTION_ID`; a `precondition` on the provider block fails the plan if the resolved
subscription differs from the expected one's **hash** — the plan refuses to run against the
wrong subscription without the repo ever carrying the id itself.

## D4 — Identity flows one way: managed identity → vault, never secrets → config

The container app gets a system-assigned managed identity with Key Vault secrets get/list and
AcrPull. Postgres credentials are generated by Terraform, written **into Key Vault**, and the
app receives only the vault URI. The connection string is composed at runtime through the
resolver — BR-010 holds in deployment exactly as it does in code review.

## D5 — The Key Vault resolver is a composition change, not a module change

`KeyVaultSecretResolver` lives beside `ConfigurationSecretResolver` in BuildingBlocks; the
host's composition root picks by configuration presence (`Secrets:KeyVaultUri`). Aspire's
`Aspire.Azure.Security.KeyVault` client integration supplies the `SecretClient` with retries,
telemetry and `DefaultAzureCredential` (managed identity in ACA, az login locally). Modules
never see any of this — `IModule.Add` structurally cannot register it (design D3 of the
connector change), which is what makes this a two-file change instead of a migration.

## D6 — Migrations run as a Container Apps Job, gated before rollout

The MigrationService image runs as a manual-trigger ACA Job with the same vault/database access.
The deploy sequence is: push image → run job → wait for exit 0 → update the app revision. The
Server keeps refusing to migrate anywhere. Deploy sequencing lives in a script the human runs
(`infra/deploy.sh`), not in CI — same policy as Terraform apply.

## D7 — CI validates, humans apply

The `terraform` CI lane runs `fmt -check` and `validate` on every PR touching `infra/`. It does
NOT plan against Azure (no credentials in CI by design — a federated identity is a later,
deliberate issue). The lane must fail loudly if it cannot run, never skip silently (ADR-0004:
a green that proves nothing is worse than a red).

## D8 — Globally unique names carry a deterministic suffix

Key Vault and container registry names are unique across **all of Azure**, not just the
subscription. The first apply proved it the hard way: `kv-aio-dev` was already taken by a
stranger and the apply failed partway through, after the resource group, database and registry
existed. Both now append `substr(sha256(subscription_id), 0, 8)` — deterministic (the same
subscription always yields the same name, so re-applies are stable), collision-free in practice,
and leaking nothing, since the full hash is already committed as the subscription guard.

The registry did not fail — `craiodev` happened to be free — and was changed anyway. A name that
works by luck in one subscription and fails in the next is a latent defect, not a working one.

## D9 — A user-assigned identity, because a system-assigned one deadlocks

Container Apps validates the registry credential *while creating the app*. A system-assigned
principal does not exist until the app is created, so `AcrPull` cannot be granted before the
thing that needs it — the app waits on a permission Terraform is waiting on the app to enable.
The first apply hung for seventeen minutes in exactly that state, with the app `InProgress` and
its identity holding no role assignments.

One user-assigned identity, created and granted before either workload, has no cycle. Both the
portal and the migration job use it: they need identical permissions, and two identities would
be two things to keep in step. `AZURE_CLIENT_ID` is passed explicitly because
`DefaultAzureCredential` will not guess between multiple assigned identities — omitting it moves
the failure from deploy time to the first vault read.

## SKU record (raise deliberately, not accidentally)

| Resource | SKU | Why |
|---|---|---|
| Container Apps env | Consumption | scale-to-zero dev portal |
| PostgreSQL Flexible | B_Standard_B1ms, 32 GB | smallest burstable; dev data is disposable |
| Container Registry | Basic | one image family, no geo-replication |
| Key Vault | standard | no HSM requirement |
| Log Analytics | PerGB2018 | ACA requires a workspace; default tier |
