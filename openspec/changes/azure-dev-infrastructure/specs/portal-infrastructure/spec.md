# portal-infrastructure

## ADDED Requirements

### Requirement: the dev environment is declared in Terraform and applied by a human

The portal's Azure dev environment SHALL be declared in Terraform under `infra/dev/` — resource
group, Log Analytics, Container Apps environment, portal container app, container registry,
PostgreSQL Flexible Server with the application database, and Key Vault — named
`aio-dev-<resource>`-style in northeurope. State SHALL live in the bootstrap storage backend.
Apply SHALL be a human action with their own Azure identity; CI SHALL run only fmt and validate,
and SHALL fail loudly when it cannot run rather than skip silently.

#### Scenario: CI touches infra

- **WHEN** a pull request changes anything under `infra/`
- **THEN** the terraform lane runs fmt-check and validate, and a failure blocks the PR

#### Scenario: apply against the wrong subscription

- **WHEN** the resolved Azure subscription differs from the expected one
- **THEN** the plan fails its precondition before any resource is touched

### Requirement: no credential enters the repository or app configuration

The subscription id SHALL reach Terraform only via gitignored variables or environment. Database
credentials SHALL be generated by Terraform and stored in Key Vault; the application SHALL
receive only the vault URI and resolve names at use through `ISecretResolver`, authenticating
with its managed identity. No connection string, password, or key SHALL appear in committed
files, container app configuration, or Terraform state outputs marked non-sensitive.

#### Scenario: reading the app's configuration in the portal

- **WHEN** the deployed container app's environment variables are inspected
- **THEN** they contain the vault URI and non-secret settings only — no password or token

### Requirement: the schema changes by the migration job, never by the Server

The MigrationService SHALL run as a Container Apps Job executed before a new Server revision
receives traffic; a non-zero job exit SHALL stop the rollout. The Server SHALL NOT migrate in
any environment — the same invariant the AppHost graph enforces locally.

#### Scenario: deploying a change that includes a migration

- **WHEN** the deploy script runs
- **THEN** the migration job completes with exit 0 before the app revision updates, and a
  failed job leaves the previous revision serving
