# Product context

> **This is a skeleton on purpose.** It ships with headings and no content, because the content is the
> one part that cannot be inherited — a plausible-looking wrong description of your product is worse
> than a blank one. The [definition of ready](./definition-of-ready.md) asks issues to cite ids from
> here; fill in what you need, when you need it, and delete the rest.

## Actors

Who acts on this system, and what each may do. Give each an id (`ACT-001`, …) — the definition of
ready asks every issue to name its main actor.

## Glossary

The vocabulary this product uses, and the words it refuses. One term per concept: an item that says
"job" where the rest of the product says "run" is an item somebody has to translate.

## Use cases

What a user can do, one entry per capability, with an id (`UC-001`, …). Product issues cite at least
one (RULE-003).

## Business rules

Invariants the system upholds regardless of which capability is being built, with an id (`BR-001`, …).
Issues name the rules they must not break.

- **BR-001 — …**

## Decisions

Decisions already taken and binding, with an id (`DEC-001`, …). A decision is recorded once and never
edited in place — a revision is a new entry that names what it revises, so the reasoning stays
readable.

- **DEC-001 — …**

## Open questions

Decisions **not yet made**, each naming what it blocks. RULE-006 forbids proposing work that depends
on one of these: a decision-closure item goes first. Move closed entries into Decisions above rather
than deleting them, so the question and its answer stay together.
