# Study: stablyai/orca

**Date:** 2026-08-11 · **Source:** <https://github.com/stablyai/orca> (TypeScript/Electron, MIT,
"The AI Orchestrator for 100x builders") · **Asked by:** the owner — _what can we take, versus
this product?_

A study, not a backlog. Nothing here was filed; the point of writing it down is that the next
person who has one of these ideas finds the reasoning instead of proposing it cold.

## What it is

A desktop cockpit for a human piloting N CLI agents (Claude Code, Codex, opencode — ~36
supported) side by side: each agent in its own git worktree on the user's machine, with
persistent terminals, an embedded Chromium ("Design Mode" sends a clicked element's HTML/CSS/
screenshot into the prompt), GitHub/Linear browsing in-app, SSH remote worktrees, a paired
mobile companion, and an `orca` CLI so agents can drive the app itself. Engineering quality is
high — a PTY-owning daemon that survives app crashes, one JSON-RPC surface over four transports,
wire compatibility kept as a documented invariant.

**The posture is the mirror image of ours.** Orca is interactive and synchronous — the unit of
work is "I launch a prompt and watch"; the agents run unsandboxed on the operator's machine, and
there is no governance: no approval gate, no caps, no per-run cost, no backlog as trigger
(GitHub/Linear are views for the human, not event sources). We are asynchronous and governed —
backlog → Automation → Agent in a sandbox of its own → PR, everything visible and accountable
from the portal. So nothing transfers as a product whole; what transfers is surgical.

## Rejected, with reasons

- **Parallel worktrees on the operator's machine.** Their isolation unit is a worktree because
  the agent shares the user's machine. Ours is a sandbox per Run by decision — stronger
  isolation, already structural. The one idea worktrees carry that sandboxes don't (fan one
  story to N attempts and compare) is taken up below as its own entry.
- **The IDE surface** — terminal splits, file explorer, editor, Design Mode, in-app GitHub/
  Linear. That is Orca's product; ours mirrors the backlog by decision (BR-008) and reviews
  output through the vendor's PR. Rebuilding a cockpit would be an Azure-portal-clone move in
  the opposite direction: a different product, not a feature.
- **SSH remote worktrees.** Their answer to "the beefy box is elsewhere". Our execution locus
  concept (#210, BR-016) already names where a Run executes; the deployed substrate is Azure by
  decision. No gap.
- **Account hot-swap and OAuth usage harvesting.** They juggle personal Claude/Codex accounts
  per developer. Our credentials are project-scoped through `ISecretResolver` (DEC-030) and
  usage is reported per Run (BR-011, DEC-038) — the multi-account problem is one we don't have.
- **The mobile companion's transport** (QR pairing, Curve25519, E2EE over a blind relay, no
  APNs/FCM). Elegant, and solving a desktop-app problem: their server is somebody's laptop, so
  they must pair peer-to-peer. Ours is a web app with a server; if notifying ever gets
  priority, web push for the Inbox is already studied and mostly grilled — see
  [2026-08-03-pr-dashboard.md](2026-08-03-pr-dashboard.md). Orca changes nothing in that
  reasoning; it only confirms the itch is real. Any notification work still revisits DEC-037
  (the website is the only surface) first, as a decision, not as a feature slipped in.

## Worth taking, when its time comes

### 1. The agent reports its own status — a live state channel inside `Executing`

The Run machine already pauses honestly (`AwaitingApproval`, `AwaitingInput`, BR-006), but
*inside* `Executing` the portal shows a growing log (UC-027) and nothing else: "working",
"stuck", and "about to ask" all look identical until the next line arrives. Orca never infers
agent state from output. It writes **managed hooks into the agent's own configuration**
(`~/.claude/settings.json` hooks, Codex `config.toml`, 14 agents) that POST status —
`working / blocked / waiting / done`, with a bounded history — to a local endpoint discovered
via an on-disk file, protocol-versioned (`src/main/agent-hooks/`, `src/shared/agent-hook-listener.ts`).

Mapped onto us: the sandbox gets an endpoint the hooks can reach, the Run records a status
timeline, and the run detail (UC-021/UC-027) shows what the agent is doing *now* — which is
also what makes waits legible before they become `AwaitingInput`. Complements, not repeats:
UC-026's Inbox (what waits on a human), #306 (answering a waiting Run from the portal), #307
(telemetry capture at session start — same "instrument the session, not the report" direction).
A grill would need: which states are worth persisting versus streaming, whether the channel is
per-runtime (it is — a hooks installer is part of the runtime seam, DEC-012), and what the
fallback is for a runtime with no hook support (Orca's answer: process-tree recognition, and
never trusting titles).

### 2. The repository declares how its sandbox is prepared

Nothing in the corpus today says how a Run's sandbox gets the repository's dependencies — the
seeded demo survives because its stories don't need `pnpm install`. Any real "implement this
and make the tests pass" story does. Orca's `orca.yaml` is the shape worth copying
(`src/shared/orca-yaml.ts`): the repo declares `scripts.setup`, shared directories, defaults —
and because the file executes commands, it is **trust-gated per version** (a human approves the
file before it runs, re-approves when it changes) and **bounds-checked** (entry counts and
field lengths capped — YAML-bomb defence).

Mapped onto us: a file in the client repository, read at dispatch, executed in the sandbox
before the agent starts; the trust gate is an Admin approval recorded on the project — pure
governance, our home ground. Touches UC-016 (implement → PR), BR-016's cleanliness stance, and
the sandbox specs. A grill would need: where approval state lives (Connector? project?), what
"changed" means (content hash), and what a Run does when setup fails (a named failure before
the agent ever runs, surely — the BR-001 lesson of one refusal, honestly stated).

### 3. Tournament runs — one story, N runtimes, compare the PRs

Orca's fan-out is manual: a human creates N worktrees with N agents and eyeballs the results.
The governed version is ours to build: an Automation dispatches the same Story to 2–3 runtimes
(or models — #245's per-Automation model choice is the natural knob), each in its own sandbox,
and the portal shows the resulting PRs side by side with per-Run cost (BR-011). That is the
feature that makes vendor-neutrality (business goal 3) *pay*: not "we support several runtimes"
but "we can tell you which one earns its cost on your backlog, with receipts".

It collides with a rule on purpose: **BR-001 says one active Run per Story**, and the collision
is the point — a tournament is one *dispatch* fanning into sibling Runs, so either BR-001 learns
a sibling-group exception or a new aggregate (a Trial? a Heat?) owns the siblings and BR-001
keeps its word per group. That decision is the heart of the grill, and it must not be made by
accident. Sequencing: after #244/#245 (runtime and model resolution) land, and after the basic
loop has survived real repositories — this is a differentiator, not plumbing. Costs are real
(N× tokens per story), which is itself an argument for the approval gate fronting it.

## Smaller habits worth noticing

- **The declarative per-agent table.** All 36 agents live in one ~350-line record set
  (`src/shared/tui-agent-config.ts`) — detection, launch, prompt-injection mode — and every
  workaround field carries a `// Why:` naming the specific upstream bug. When our runtime seam
  grows its third implementation (business goal 3 says it must be trivial), this is the shape
  that keeps it honest: config plus documented quirks, not a class hierarchy.
- **`preflightTrust`.** Orca pre-writes each agent's "trust this folder" marker before launch,
  because the first-run trust menu otherwise swallows the injected prompt. Every Run of ours
  starts an agent in a pristine sandbox — we will hit this exact failure mode, and it fails
  silently. Worth a line in the runtime adapters the day one of them grows a trust prompt.
- **Terminal state as checkpoints.** Their daemon runs a headless xterm per session and
  serializes ANSI checkpoints (snapshot + scrollback + modes), so a reattaching client replays
  checkpoint + tail instead of raw history (`src/main/daemon/history-manager.ts`). Directly
  relevant to UC-029's sandbox terminal and #308's attach surface: what a human sees on
  reattach is a solved problem, and this is the solution's shape.
- **Wire compatibility as a documented invariant.** `docs/reference/remote-wire-compatibility.md`
  states which changes are safe (new optional field) and which need capability negotiation (new
  opcode), because old decoders drop unknown frames silently. Cheap to adopt the day our portal
  ↔ sandbox transport gets a second consumer.
